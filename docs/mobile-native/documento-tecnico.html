Cómo construimos la app nativa del operador

La solución completa para llevar la visión de chat, incendios y órdenes a Kotlin y Jetpack Compose: el build, los módulos, la navegación, cada pantalla con sus componentes, los datos y la sincronización, el backend con Jev, la seguridad, las pruebas y el orden de construcción. Los nombres de componentes y las buenas prácticas salen de los skills oficiales de Android (github.com/android/skills).

00 · Resumen

Una app Android nativa, una sola Activity, tres pilas de navegación y Room como única fuente de verdad. Jev nunca se llama desde el teléfono: decide en el backend, con el motor de decisiones que ya existe en el PR #372, y la app pinta lo que llega por SSE o por push.

En el teléfono

  • Kotlin, Compose y Material 3, sobre AGP 9.
  • Navigation 3 con tres pilas: Chats, Incendios y Órdenes.
  • Room, WorkManager y FCM, para que nada se pierda sin señal ni con la app cerrada.

En el backend

  • Los endpoints nuevos viven en el plugin chats, que es dueño de las conversaciones.
  • Burbujas y vigía son dos cuestionarios y dos políticas del motor de decisiones.
  • El oráculo es Jev con id fijo, anonimizado y con tiempo máximo.

Cómo se verifica

  • Tests JVM, Compose sobre Robolectric y screenshots.
  • UI Automator para notificaciones y widget.
  • Un journey del Android CLI por cada flujo de la visión.

01 · Build y configuración

AGP 9, Kotlin integrado y R8 completo

El proyecto nace en AGP 9, así que no hay migración pendiente. Tres consecuencias que marca el skill agp-9-upgrade:

  • Kotlin integrado: no se aplica el plugin kotlin-android, y las opciones del compilador van en kotlin { compilerOptions { } }.
  • KSP para todo (Hilt, Room): nada de kapt. KSP 2.3.6 o más y Hilt 2.59.2 o más.
  • DSL nuevo: las APIs viejas de variantes no existen. La lógica común vive en plugins de convención (build-logic/), no en scripts copiados.

Requisitos de herramientas: Gradle 9.1 o más, JDK 17 y build tools 36. Las versiones de cada librería se fijan en gradle/libs.versions.toml; nada de versiones dinámicas ni de alfas en los módulos centrales.

02 · Módulos y arquitectura

Seis capas, una responsabilidad cada una

Figura 1 · Las capas de la app. Los datos son la única fuente de verdad; el motor SDUI y su contrato son Kotlin puro y se prueban en la JVM.

  • Flujo unidireccional en toda la app. La UI solo emite eventos y pinta estado. El estado sale de un StateFlow que la pantalla lee con collectAsStateWithLifecycle().
  • MVI en el motor SDUI (reducer puro, un SurfaceViewModel genérico) y un ViewModel propio en cada isla nativa: timeline, composer, cámara y radar. Es lo que definió el documento de arquitectura del 28 de septiembre.
  • Offline primero: la red escribe en Room y la UI lee de Room. Ninguna pantalla espera una respuesta HTTP para pintarse.
  • Todas las claves de navegación viven en :core:navigation y cada funcionalidad es un módulo que registra sus entradas por multibinding de Hilt (receta modular de Navigation 3). Un módulo navega a otro sin conocer su implementación, sin necesitar el par api/impl por funcionalidad.

03 · Navegación

Tres pilas, escenas y un radar que no es pantalla

Figura 2 · Cada destino de primer nivel tiene su pila. El radar abre el caso en Incendios; «Volver a Laura» cambia a la pila de Chats, donde el chat sigue intacto; un deep link arma una pila sintética.

  • Tres destinos de primer nivel con NavigationSuiteScaffold: barra inferior en el teléfono y riel en la tablet o el plegable abierto (skill adaptive). Cada destino tiene su propia pila (receta multiple back stacks) y Chats es la pila de inicio: se sale de la app siempre por ahí.
  • La pila es una lista de claves @Serializable guardada con rememberNavBackStack. Sobrevive a la rotación y a que el sistema mate el proceso.
  • Escenas: la ficha de la orden, «+ Más» y el selector de productos son entradas con metadata de hoja inferior (la BottomSheetSceneStrategy de la receta oficial). En pantallas anchas, bandeja y chat se ven lado a lado con ListDetailSceneStrategy, sin ListDetailPaneScaffold, como pide el skill.
  • Decoradores por entrada: SaveableStateHolder (scroll y campos), ViewModelStore (un ViewModel por clave, con hiltViewModel y fábrica asistida) y ResultEventBus para devolver resultados: el selector de productos le devuelve al chat lo elegido con ResultEffect.
  • «Volver a Laura» no es un pop: cambia de pila. El chat de Laura sigue arriba de la pila de Chats con su ViewModel vivo; el borrador, además, está en Room.
  • El radar no es una clave. Es una capa encima del NavDisplay. Si está desplegado, el gesto de atrás lo pliega con NavigationBackHandler (skill navigation-event: en SDK 36 o más no se usa el BackHandler viejo). Todo lo demás usa el retroceso de Navigation 3.
  • Los clics que navegan van envueltos en dropUnlessResumed, para que un doble toque no apile dos pantallas.

@JvmInline @Serializable value class SessionId private constructor(val raw: String) {
    companion object { fun parse(raw: String): SessionId? = raw.takeIf(SessionIdFormat::matches)?.let(::SessionId) }
}

Raíz y registro por módulo

// :app — la raíz: tres pilas (receta multiple back stacks), escenas y el radar encima
typealias EntryProviderInstaller = EntryProviderScope<NavKey>.(Navigator) -> Unit

@Composable
fun OperatorNavHost(installers: Set<EntryProviderInstaller>) {
    val state = rememberNavigationState(startRoute = InboxKey, topLevelRoutes = setOf(InboxKey, FiresKey, OrdersKey))
    val navigator = remember(state) { Navigator(state) }
    val sheets = remember { BottomSheetSceneStrategy<NavKey>() }       // copiada de la receta oficial
    val listDetail = rememberListDetailSceneStrategy<NavKey>()         // adaptive-navigation3: dos paneles en tablet
    val provider = entryProvider { installers.forEach { install -> install(navigator) } }

    NavigationSuiteScaffold(navigationSuiteItems = { topLevelItems(state.topLevelRoute, navigator::navigate) }) {
        BoxWithConstraints(Modifier.fillMaxSize()) {
            NavDisplay(
                entries = state.toDecoratedEntries(provider),  // SaveableStateHolder + ViewModelStore por entrada
                onBack = navigator::goBack,
                sceneStrategies = listOf(sheets, listDetail),
            )
            RadarHost(maxHeight = maxHeight * 0.75f, onOpen = navigator::openFire)   // capa: no es una clave
        }
    }
}

Deep links: notificaciones y widget

La notificación y el widget abren la app con un intent explícito a MainActivity que trae hubara://live/{id} o hubara://order/{id}. No hace falta anunciar ese esquema con un intent-filter, así que ninguna otra app lo ve. Igual se valida siempre, porque MainActivity está exportada por ser el launcher. Cada link arma una pila sintética: desde una notificación de Carlos, atrás vuelve a Incendios en vez de cerrar la app.

// :app — MainActivity (launchMode singleTop). La notificación y el widget la abren con un intent EXPLÍCITO
// que trae data = hubara://live/{id}. No hay intent-filter para ese esquema: ninguna otra app lo anuncia.
override fun onCreate(savedInstanceState: Bundle?) {
    enableEdgeToEdge()                                      // antes de setContent (skill edge-to-edge)
    super.onCreate(savedInstanceState)
    pendingLink.value = DeepLinks.parse(intent?.data)       // valida: esquema, ruta e id con formato estricto
    setContent { OperatorTheme { OperatorApp(pendingLink) } }
}

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)                                       // skill android-intent-security
    pendingLink.value = DeepLinks.parse(intent.data)        // mismas reglas que en onCreate
}

// hubara://live/{id} → pila sintética de Incendios: [FiresKey, LiveKey(id)]. Atrás vuelve a Incendios, no sale.
object DeepLinks {
    fun parse(uri: Uri?): SyntheticStack? = when {
        uri?.scheme != "hubara" -> null
        uri.host == "live" -> SessionId.parse(uri.lastPathSegment.orEmpty())?.let { SyntheticStack(FiresKey, listOf(LiveKey(it))) }
        uri.host == "order" -> OrderId.parse(uri.lastPathSegment.orEmpty())?.let { SyntheticStack(OrdersKey, listOf(OrderSheetKey(it))) }
        else -> null                                        // un link inválido no navega
    }
}

Cómo llegan las burbujas

La app no calcula burbujas: las recibe. El backend corre el bucle de juego de la visión en cada tick y manda el resultado por SSE. La app solo las pinta, las ordena como vienen y ejecuta lo que el operador toca.

Figura 3 · Un tick de punta a punta. El motor pregunta a Jev en un request o, si Jev falla o tarda, aplica la regla por etapa. La app recibe las burbujas por SSE y el toque vuelve como POST idempotente.

Evento que recibe la app

{
  "type": "mobile.suggestions",
  "session_id": "<sesión>",
  "version": 17,
  "decided_by": "jev",
  "stage": "etapa_variantes",
  "suggestions": [
    { "id": "s1", "label": "Enviar aromas", "prominence": "primary", "confidence": 0.91,
      "action": { "name": "present_variant_picker", "args": { "product": "duo-zodiacal" } }, "editable": true },
    { "id": "s2", "label": "Pedir datos de envío", "prominence": "normal", "confidence": 0.72,
      "action": { "name": "request_shipping_details", "args": {} }, "editable": false }
  ]
}
  • La prominencia la decide el servidor (primary, normal). Los umbrales viven en el perfil del motor, así que se ajustan sin publicar una versión de la app.
  • version ordena los eventos: uno más viejo que el que ya está se descarta.
  • decided_by dice si decidió Jev o la regla de respaldo. Va al log de calibración junto con lo que tocó el operador.
  • Al abrir un chat se piden las burbujas actuales por REST; después llegan por SSE.

Enviar con cinco segundos para deshacer

Tocar una burbuja escribe la acción en Room (el mensaje aparece como «enviando») y la encola en WorkManager con cinco segundos de espera y un nombre único. «Deshacer» cancela ese trabajo. Como vive en WorkManager y no en memoria, un envío confirmado no se pierde aunque el sistema cierre la app. El servidor deduplica por client_action_id, así que un reintento nunca manda dos veces.

// :core:data — tocar una burbuja: se escribe en Room (aparece «enviando») y se encola con 5 s de espera.
// «Deshacer» cancela el trabajo por su nombre único. Sobrevive a que el sistema mate la app.
suspend fun send(suggestion: Suggestion, session: SessionId) {
    val id = ClientActionId.new()
    outbox.insert(OutboxEntity(id, session, suggestion.action, state = PENDING_UNDO))
    val work = OneTimeWorkRequestBuilder<RunToolWorker>()
        .setInitialDelay(5, TimeUnit.SECONDS)
        .setInputData(workDataOf(RunToolWorker.KEY_ID to id.raw))
        .setConstraints(Constraints(requiredNetworkType = NetworkType.CONNECTED))
        .build()
    workManager.enqueueUniqueWork(id.raw, ExistingWorkPolicy.KEEP, work)
}

fun undo(id: ClientActionId) = workManager.cancelUniqueWork(id.raw)

@HiltWorker
class RunToolWorker @AssistedInject constructor(
    @Assisted ctx: Context, @Assisted params: WorkerParameters,
    private val api: OperatorToolsApi, private val outbox: OutboxDao,
) : CoroutineWorker(ctx, params) {
    override suspend fun doWork(): Result {
        val item = outbox.get(inputData.getString(KEY_ID)!!) ?: return Result.success()
        return when (val r = api.runTool(item.session, item.action, clientActionId = item.id)) {  // idempotente
            is ToolResult.Sent -> { outbox.markSent(item.id, r.messageId); Result.success() }
            is ToolResult.WindowClosed -> { outbox.markFailed(item.id, WINDOW_CLOSED); Result.failure() }  // 409
            is ToolResult.Transient -> if (runAttemptCount < 5) Result.retry() else Result.failure()
        }
    }
    companion object { const val KEY_ID = "client_action_id" }
}

05 · Radar, Incendios y órdenes

Lo grave aparece al instante, sin quitarle el foco al teclado

Figura 4 · Un incendio grave en la app. Con la app abierta aparece el radar sin pedir foco; con la app cerrada llega una notificación privada que abre un deep link validado.

Por qué el radar no le quita el foco al composer

  • Vive en la misma ventana. Es un composable encima del NavDisplay, no un Dialog ni un Popup enfocable: esos abren otra ventana y el teclado se cierra.
  • No es enfocable: focusProperties { canFocus = false }. Nunca llama a FocusRequester ni a clearFocus(), y no toca el controlador del teclado.
  • No se abre por accidente: la tarjeta no responde al toque durante el primer medio segundo, por si el dedo iba a una tecla.
  • Se anuncia sin interrumpir: liveRegion = Polite hace que TalkBack la lea cuando termine lo que está leyendo.
  • No tapa el composer: el chat marca su parte de abajo (deshacer, burbujas y composer) como el piso del radar (RadarFloor); lo que aparece solo nunca baja de ahí, con o sin teclado.
  • Varios seguidos se juntan: si llegan varios graves mientras escribes, se apilan con el más nuevo arriba (máximo 3 y una línea «Ver N más») y se pliegan juntos 4 s después del último (RadarBurst). Antes cada tarjeta reemplazaba a la anterior y la primera casi no se veía (lo mostró el escenario S14 en el emulador).
  • Sin sonido mientras escribes: solo una animación corta y una háptica suave.
  • Se pliega solo: la tarjeta de un incendio nuevo se ve 4 segundos, compacta y debajo del encabezado, y después queda como un chip en la barra superior (RadarIndicator). La prueba de punta a punta mostró que una tarjeta fija arriba tapaba «Tomar la conversación»; con el chip, el radar nunca cubre botones.

    val haptics = LocalHapticFeedback.current
    LaunchedEffect(cards.firstOrNull()?.id) { if (cards.isNotEmpty()) haptics.performHapticFeedback(HapticFeedbackType.ContextClick) }

    var expanded by rememberSaveable { mutableStateOf(false) }
    NavigationBackHandler(                                          // skill navigation-event (no BackHandler viejo)
        state = rememberNavigationEventState(currentInfo = NavigationEventInfo.None),
        isBackEnabled = expanded,
        onBackCompleted = { expanded = false },
    )

        Column(
            Modifier
                .windowInsetsPadding(WindowInsets.statusBars)

                .focusProperties { canFocus = false }               // no le quita el foco al TextField
                .semantics { liveRegion = LiveRegionMode.Polite }   // TalkBack lo anuncia sin interrumpir
        ) {
            val visible = if (expanded) cards else cards.take(1)
            visible.forEach { card ->

                }
            }

        }

// :core:network — un solo stream por app en primer plano. Ticket nuevo en cada reconexión (#181, SEC-06).
class EventStream @Inject constructor(
    private val client: OkHttpClient, private val tickets: SseTicketApi, private val json: Json,
) {
    fun events(): Flow<ServerEvent> = callbackFlow {
        val ticket = tickets.mint().ticket                                   // POST /api/dashboard/sse-ticket
        val request = Request.Builder().url("$BASE_URL/api/dashboard/events?ticket=$ticket").build()
        val source = EventSources.createFactory(client).newEventSource(request, object : EventSourceListener() {
            override fun onEvent(eventSource: EventSource, id: String?, type: String?, data: String) {
                trySend(ServerEvent.decode(json, type, data))                // tipos desconocidos → ServerEvent.Unknown
            }
            override fun onFailure(eventSource: EventSource, t: Throwable?, response: Response?) { close(t) }
        })
        awaitClose { source.cancel() }
    }.retryWhen { _, attempt -> delay(backoff(attempt)); true }            // 1 s → 30 s con jitter
}

def decide(facts: FireFacts, reading: Reading, th: Thresholds) -> FireDecision:
    if not reading.ok:                                   # Jev falló o tardó: decide la regla de hoy
        return rules_fallback(facts)                     # ruta humano con espera, motivo de escalamiento, atraso
    if reading.p("fire.worth_it") < th.worth_it:
        return FireDecision.none()                       # queda en el chat o en la ficha
    kind = reading.choice("fire.kind")
    doubt = reading.confidence("fire.kind") < th.doubt
    grave = reading.score("fire.severity") >= th.grave and not doubt and kind != "felicitacion"
    return FireDecision(show=True, grave=grave, kind=kind,
                        worse=reading.p("fire.getting_worse", default=0.0) >= 0.5)

¿Jev directo a OpenRouter desde el teléfono, o por nuestro servidor?

Por nuestro servidor. La intuición de ir directo para ahorrar latencia no se cumple, porque el turno de la burbuja empieza en el servidor y no en el teléfono:

  • Directo: el mensaje del cliente llega al webhook → el servidor lo manda al teléfono por SSE → el teléfono arma el estado y llama a OpenRouter → responde. Son dos saltos en serie antes de Jev.
  • Por el servidor: el mensaje llega al webhook → el servidor llama a Jev en ese mismo momento, mientras le avisa al teléfono → la burbuja llega por SSE junto con el mensaje, o justo después. El operador no espera a Jev al abrir el chat: la burbuja ya está calculada.
  • El salto extra es mínimo: servidor → OpenRouter es de centro de datos a centro de datos (del orden de decenas de milisegundos). Jev solo, medido en el PR #372, tarda 0,55 s de mediana y 1,06 s como máximo.

Y hay razones que no son de latencia:

  • La llave de OpenRouter no puede vivir en el APK: se extrae en minutos y cualquiera gasta a nuestra cuenta.
  • La anonimización de nombres y el «sin retención» del proveedor ya los hace el oráculo del servidor.
  • El tablero y las jugadas legales salen del vault (borrador, etapa, ventana de 24 h, catálogo): copiarlos al teléfono duplica la lógica y abre la puerta a burbujas que no aplican.
  • El vigía tiene que correr con la app cerrada, así que de todos modos vive en el servidor.
  • La API de decisiones está en alfa: si cambia de forma, se arregla en el servidor sin publicar una versión de la app.

La app ya consume las burbujas como un endpoint más (GET /api/chats/mobile/suggestions/ y el SSE). Hoy responden reglas; cuando Jev entre, la app no cambia.
