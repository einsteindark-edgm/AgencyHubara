App Operador · Firebase Cloud Messaging

Activar los avisos push

Con esto, un incendio grave le llega al teléfono del operador en segundos aunque la app esté cerrada, y el widget de ventas calientes se actualiza solo. Hoy, con la app cerrada, el teléfono revisa cada 15 minutos. El código ya está hecho; faltan tres cosas que solo puedes hacer tú: crear el proyecto de Firebase, cargar dos llaves en AWS y probar en el teléfono.

0 de 12 pasos

Lo que necesitas

  • Una cuenta de Google (la de la empresa). Firebase Cloud Messaging es gratis, sin límite de avisos.
  • Tu acceso de administrador a AWS, el mismo con el que cargaste los otros secretos (Jev, WhatsApp).
  • GitHub, para aprobar el terraform apply y lanzar el deploy.
  • El teléfono del operador con Google Play (cualquier Android normal, el Motorola sirve).

Ya quedó hecho

  • La app pide su configuración de Firebase al servidor y se registra sola al abrir.
  • El backend detecta el incendio grave nuevo y manda el aviso; borra los teléfonos que ya no existen.
  • Terraform declara las dos llaves; el script las sube desde los archivos que bajes.
  • «Más → Probar avisos» en la app, y el escenario S20 en el emulador.
Las llaves nunca van al chat ni al repo. El repositorio es público. Los dos archivos que vas a bajar de Firebase se quedan en una carpeta tuya fuera del repo y llegan a AWS con el script del paso 6.
Fase A · en Firebase · unos 20 minutos

El proyecto y sus dos archivos

Puedes hacerla hoy, antes de mergear el PR. Al final tendrás dos archivos JSON en tu computador.

Crea el proyecto de Firebase

Lo haces tú5 min
  1. Entra a la consola de Firebase con la cuenta de Google de la empresa y elige Crear un proyecto.
  2. Ponle un nombre que reconozcas, por ejemplo hubara-operador. Firebase le arma un id único (por ejemplo hubara-operador-a1b2c); no hace falta anotarlo.
  3. Cuando pregunte por Google Analytics, desactívalo: la app no lo usa y así no recoge datos de más.
  4. Termina con Crear proyecto. Queda en el plan gratuito (Spark), que alcanza para los avisos.
Oficial: Consola de Firebase · Agregar Firebase a una app Android

Registra la app Android y baja google-services.json

Lo haces tú5 min
  1. En la página del proyecto toca el ícono de Android (Agregar app).
  2. Nombre del paquete, exactamente: com.hubara.operator. Apodo: App Operador. El SHA-1 no hace falta para los avisos: déjalo vacío.
  3. Registrar app → Descargar google-services.json. Guárdalo en una carpeta tuya fuera del repo, por ejemplo ~/hubara-secretos/.
  4. Los pasos siguientes del asistente (copiar el archivo a la app, agregar el plugin de Gradle, el SDK) sáltatelos con «Siguiente» hasta terminar: la app ya trae Firebase y recibe esa configuración desde el servidor.

Revisa que la API de Cloud Messaging (V1) esté activa

Lo haces tú1 min
  1. Ícono de engranaje → Configuración del proyecto → pestaña Cloud Messaging.
  2. En «API de Firebase Cloud Messaging (V1)» debe decir Habilitada. En proyectos nuevos viene así.
  3. Si dice inhabilitada: menú ⋮ de esa fila → «Administrar API en Google Cloud Console» → Habilitar.
  4. La «API heredada» (legacy) no se usa: Google la apagó. No la actives.

Genera la llave de la cuenta de servicio

Lo haces tú3 min

Es la llave con la que el backend firma cada aviso. Trátala como una contraseña.

  1. Configuración del proyecto → pestaña Cuentas de servicio → «SDK de Firebase Admin».
  2. Generar nueva clave privada → confirmar. Baja un archivo como hubara-operador-a1b2c-firebase-adminsdk-xxxxx.json. Guárdalo junto al anterior.

Más seguro (opcional, 5 min): esa cuenta puede administrar todo el proyecto de Firebase. Como el proyecto solo sirve para los avisos, el riesgo es bajo; si prefieres una llave que solo pueda mandar avisos:

  1. Google Cloud Console (mismo proyecto) → IAM y administración → Cuentas de servicio → Crear, nombre avisos-app-operador.
  2. Rol: Administrador de la API de Firebase Cloud Messaging (roles/firebasecloudmessaging.admin).
  3. En la cuenta creada: Claves → Agregar clave → Crear clave nueva → JSON. Usa ese archivo en vez del anterior.

Si Google dice que la creación de claves está bloqueada por una política de la organización (iam.disableServiceAccountKeyCreation), la cuenta de Google pertenece a un Workspace con esa regla: pide al administrador una excepción para este proyecto, o crea el proyecto con una cuenta fuera de esa organización.

Fase B · en AWS · unos 15 minutos

Las llaves en SSM y el backend nuevo

Después de mergear el PR #385. Los comandos van desde la raíz del repo, en main actualizado.

Crea los dos parámetros con Terraform

Lo apruebas tú5 min

Toda llave nace en Terraform (así la hereda el siguiente tenant). El apply crea FCM_SERVICE_ACCOUNT_JSON y FIREBASE_ANDROID_CONFIG_JSON con un valor de relleno.

  1. Mira el plan del último terraform-plan de main: debe crear esos dos parámetros. Si trae otros cambios, son pendientes de antes (el plan de despliegue de #372): pregúntame antes de aprobar.
  2. Lanza el apply y apruébalo en GitHub (entorno production):
gh workflow run terraform-apply.yml --ref main -f root=platform

Sube las dos llaves con el script

Lo haces tú3 min
  1. Crea el archivo infra/scripts/secrets.firebase.env con estas dos líneas, cambiando las rutas por las de tus archivos. Git lo ignora (todo *secret*.env en esa carpeta).
FCM_SERVICE_ACCOUNT_JSON=@~/hubara-secretos/hubara-operador-a1b2c-firebase-adminsdk-xxxxx.json
FIREBASE_ANDROID_CONFIG_JSON=@~/hubara-secretos/google-services.json

La @ le dice al script que lea el archivo y lo suba en una sola línea. Si un archivo está mal, el script dice cuál y no sube nada.

  1. Súbelas con tu perfil de AWS de administrador:
python3 infra/scripts/aws_bootstrap.py secrets --tenant hubara --file infra/scripts/secrets.firebase.env

Confirma que ya no están en relleno

Lo haces tú1 min

El bucket es el del state de Terraform (la variable TF_STATE_BUCKET de GitHub). El script solo lista nombres: ningún valor sale de AWS.

python3 infra/scripts/aws_bootstrap.py verify --tenant hubara --bucket TU_BUCKET_DE_STATE

Ninguna de las dos debe aparecer como pendiente.

Redespliega el backend

Lo haces tú5 min

El deploy vuelve a armar el .env del servidor desde SSM; sin él, el backend sigue sin llaves.

gh workflow run backend-deploy.yml --ref main

Al arrancar, el log del API dice [chats.mobile] avisos push encendidos (fcm_v1). Si no lo ves, no pasa nada: el paso 11 lo comprueba desde el teléfono.

Fase C · en el teléfono · unos 5 minutos

Registrar y probar

Instala la versión nueva de la app

Lo haces tú5 min

La que sale de main después del merge. Si la distribuyes por la prueba interna de Google Play, sube un .aab nuevo: si ya subiste la versión 1, esta necesita versionCode 2 (en android_operator/app/build.gradle.kts; pídemelo y lo dejo listo). La receta está en la guía de Google Play.

Abre la app con internet

Lo haces tú1 min

Con la sesión iniciada, la app pide al servidor la configuración de Firebase, lo arranca y registra el teléfono. No hay botón: pasa solo. En Android 13 o más nuevo acepta el permiso de notificaciones si lo pide (el Motorola con Android 11 no lo pide).

Prueba con «Más → Probar avisos»

Lo haces tú1 min

Abajo dice «Listo: el aviso de prueba te llega en unos segundos» y llega la notificación «Los avisos funcionan». Ese aviso hizo el viaje completo: el backend, Google y el teléfono. Si sale otro mensaje, está en la tabla de abajo.

La prueba de verdad: con la app cerrada

Lo haces tú3 min
  1. Cierra la app del todo (deslízala fuera de Recientes) y bloquea el teléfono.
  2. Desde tu número de prueba, escríbele a la tienda que quieres hablar con una persona.
  3. En segundos debe llegar el aviso del incendio grave. Tócalo: abre el chat.

Si «Probar avisos» llega pero esto no, casi siempre es el ahorro de batería: en el teléfono, Configuración → Apps → Operador → Batería → Sin restricciones, y revisa que el canal «Incendios graves» no esté silenciado.

El recorrido de un aviso

  1. Un cliente espera a una persona; el backend ve que el incendio pasó a grave.
  2. El backend le pide a Google que despierte los teléfonos registrados.
  3. Google entrega el aviso. Solo dice «ponte al día»: ni nombres, ni mensajes, ni teléfonos.
  4. La app despierta, lee el backend con su sesión y arma la notificación.

Cuándo avisa

  • Incendio grave nuevo: aviso urgente, al momento.
  • Cambian las ventas calientes: el widget se actualiza, como mucho cada 2 minutos.
  • Si un aviso se pierde, el teléfono igual revisa cada 15 minutos.
  • Para apagarlo: borra la llave en Firebase (Cuentas de servicio) o vuelve a dejar el relleno en SSM y redespliega. La app sigue con su revisión de 15 minutos.
